### Breaking

- `/feature` now requires a `change-prefix:` line in `.harness-version`, in every repository, whether or not a `spec_product:` is set. It is the prefix the System Registry issued for your repository (`MYPR`, giving change keys like `MYPR-7`). Without the line, `/feature` stops at phase 0 and tells you which line to add; nothing else runs. Add it once, before your next feature.
- Every `/feature` now opens a work item on your tracker at the start, titled `<KEY>: <title>`, and names the feature branch after the key (`mypr-7-<slug>`). Until now that happened only in repositories connected to Spec Universe.
- A touched-set record written before this version (`features/<slug>.md` on your `coordination` branch) is refused by the overlap report until its next refresh brings a journey position. An in-flight feature is not lost: `node .claude/scripts/touched-set.mjs refresh --from=<record> --phase=<position>` completes it, and a resumed `/continue` does that for you.

### Features

- Every `/feature` now leaves an artefact per journey position, so a person or the Product Cockpit can see where a change is without inferring it. The touched-set record carries a required `phase` field holding one of the 23 lifecycle positions the cockpit draws (`captured`, `challenging`, `challenged`, ... `built`); `/feature` writes it at every phase boundary, twice per transition, `/continue` rewrites it on resume, and `/to-preprod` deletes the record at the merge. From `verified` on, the cockpit reads GitHub instead.
- `/feature` phase 1 is now four transitions with two gates: a short grill on the WHY that ends in pursue, drop or park; the grill on the how; an impact assessment (the touched set in full, every conflict decided); and the build decision (build, drop or park). The challenged why lands on the work item under `## Challenge` with the `pursue` label; `park` labels the open work item `parked`; `drop` closes it as not planned.
- `.claude/JOURNEY.md` ships with the harness and is the one place that says, per position, which skill does the work, which artefact it leaves, when a transition is ready and when it is done, how either can be seen, and what blocked means. It is harness-managed, so an upgrade keeps it current.
- Standing down on a blocker is a defined act: a `## Blocked` section in the feature context, the `blocked` label on the work item, and one ask on the Product Cockpit's Board through the new `.claude/scripts/board.sh` (`BOARD_URL` and `BOARD_TOKEN` in the environment), only when a person is what unblocks it. The phase is left alone on purpose: a stalled record goes stale and the cockpit shows the change back at the last state it completed.

### Notes

- Quick mode (`/feature --quick`) still works and now writes `captured` then `building`, so the journey shows honestly that four states were skipped.
- `/feature` phase 5 and `/to-preprod` write no journey position past `built`; the check on the pushed head, the pull request, the merge and the release are what the cockpit reads for the rest of the journey.
