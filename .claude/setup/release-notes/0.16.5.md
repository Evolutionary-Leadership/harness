### Features
- `/feature --ship` runs a change from capture to its exit without stopping at a gate. Pass it when nobody is going to be reading the session: it answers the gates itself, takes the exit your repository already permits, and comes back when the work is filed or when it genuinely cannot proceed. It composes with `--quick` and works without it.
- `--ship` never grants itself an exit. What it may take is read from `.harness-version` at the start of the run and reported there, so you learn at the beginning rather than the end. A `reviewers:` list means it opens a pull request and leaves it for your reviewers; a `release` entry in `agent-authority:` means it can ship to production; anything else means it merges to the staging branch and says that is as far as it went.
- `--ship` still stands down. It answers "shall I continue?" in advance and "which way?" never, so a merge conflict carrying two incompatible intents, a check whose failure cannot be explained, an architecturally significant review finding, or a design decision nobody settled beforehand each stop the run and report a block as usual. It never skips the full check, the regression test for a bug fix, or the work item.

### Notes
- A flag is not authority. `/release` now says in as many words that `--ship` is not a user asking for a release, so an unattended run reaches production only where `agent-authority:` grants `release` in your `.harness-version`. Adding or removing that line is how you decide, and it is the only thing that decides it.
- `--ship` does not survive the session. A resumed `/continue` does not re-arm it, and the feature context records that the run used it, so a later reader can see why the run carries no approvals.
