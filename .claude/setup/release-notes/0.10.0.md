### Features
- Your project can now connect its code to a specification held outside the repository, in Spec Universe, and have a check prove that connection on every branch. The whole capability arrives asleep: until you set `spec_product` in `.harness-version`, `check-spec` prints one line, `spec loop not connected`, and exits 0 without reading a credential. Nothing your project does today changes.
- To turn it on, add three keys to `.harness-version`: `spec_product` (the product slug in Spec Universe, and the switch itself), `change-prefix` (the prefix your change keys carry, issued once and never reissued), and `gate-mode` (`evaluate` or `enforce`; leave it out and you get `evaluate`). Set `SPEC_UNIVERSE_URL` and `SPEC_UNIVERSE_TOKEN` as repository secrets. There is no URL key: the base URL travels with the token.
- Once connected, five skills gain steps they did not have. `/code-review` grows a Spec axis that compares behaviour against the specification and must show its evidence. `/to-spec` sweeps for statements your change contradicts and makes you choose, per node, between amending it, retiring it, and conforming to it. `/feature` opens with a Capture phase and mints a change key. `/to-preprod` runs a gate over the specification before the merge. `/release` writes conformance back and closes the work item.
- `/feature` will refuse to guess when your change contradicts something the specification already promises. It shows the statement verbatim with what cites it and what is bound to it, and waits for your decision rather than warning and continuing.

### Fixes
- A release whose files all sit outside your `railway.json` watch patterns no longer waits forever for a deploy that will never happen. It is verified by equivalence, says so, and finishes. Before this, a documentation-only release left its work item open and needed closing by hand.
- Your branch checks now receive the Spec Universe credentials from repository secrets as part of the harness-managed workflow. If you had added that block to `.github/workflows/feature-branch-checks.yml` yourself, an upgrade touching that file would have deleted it silently. You can now remove your copy.

### Notes
- The specification check is **fail closed** and has no offline cache by design. If it cannot read the specification, your build stops. A check that goes green while blind turns an unverified build into one that looks verified, which is worse than having no check.
- An unset credential and a refused credential are configuration faults, not outages, and the check says so in different words for each. If your gate turns red immediately after an upgrade, look at the secrets before you look at the network.
- Coverage is keyed on a node's `status`. A `live` node with nothing anchored to it fails the build; a `planned` node is reported as backlog. So a newly connected project starts with everything `planned` and nothing that hurts, and arms the gate one node at a time. Leaving every node `planned` forever leaves the gate switched off.
- Connecting a project needs one edit the upgrade cannot make for you: `check-spec.mjs` carries tree constants (which directories hold your domain code and your prose) that describe the project it was written in. Edit them once when you connect, and re-apply after an upgrade that changes the file. This is stated rather than hidden because the file is harness-managed and will overwrite your edit.
- The convention document arrives as `.claude/SPEC-LOOP.md` rather than under `docs/`. `docs/` files are written once and never overwritten, so a new document there would have arrived without a row in your `docs/README.md` index, and the documentation checker fails on an unindexed document. Putting it in the managed tree means it reaches you on upgrade and owes no index row.
