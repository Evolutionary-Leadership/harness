### Breaking
- Upgrades now come from this public template repo. Open `.harness-version`:
  if its `repo:` line names anything other than
  `Evolutionary-Leadership/harness`, change that one line to say exactly
  that, then run `/harness-upgrade` again. Until you do, the upgrade cannot
  read its source, which is why it has been failing with a confusing "not
  found" rather than a permission error. It is a hand edit because the skill
  that knows the new address cannot be fetched from the old one.
- The `companion_url:` and `traits:` lines are gone from `.harness-version`.
  Nothing read `companion_url`; the API it pointed at was never built.
  Delete both lines, or leave them; they are ignored either way.
- Managed trait files are no longer installed or updated. If you have a
  `.claude/traits/` directory it is now yours: nothing will overwrite it,
  and nothing will update it. Any line in your `CLAUDE.md` telling the agent
  to read it still works.

### Features
- `/harness-upgrade` shows what changed and why, not just which files it
  would write. Breaking items appear above the confirmation prompt, because
  applying an upgrade does not perform them.
- `/harness-upgrade <version>` now applies that version's content. It used
  to filter the change list while still fetching the latest files, so asking
  for an older version gave you the newest content.
- Retired files can be removed. Files the harness has dropped are offered
  for deletion instead of accumulating, and only inside directories the
  harness owns. Removals are always confirmed separately.
- Upgrades need no credentials and no repository access beyond the public
  template repo.

### Fixes
- A project stamped with a variant name that no longer exists gets a real
  upgrade plan. It used to report "nothing to do" and change nothing,
  silently, which affected the oldest projects.
- An upgrade no longer misses a managed file you had edited by hand. The
  plan is built by comparing your repository against the target version's
  actual tree, so local edits are seen rather than assumed away.
- One-shot setup files are never restored into a configured project. The
  published tree carries the setup machinery for fresh scaffolds, and an
  upgrade now refuses those paths outright rather than leaving a setup
  step armed in a repository that must not run it again.
- Your `README.md`, `LICENSE` and `NOTICE` are never overwritten by the
  template's own copies, which sit at those same paths upstream.

### Improvements
- Upgrades are faster and no longer hit request limits. Version discovery
  and content fetch are git operations rather than API calls, so a large
  upgrade cannot be truncated or rate limited part way through.
- `.harness-version` is amended rather than rewritten: only its `version:`
  line changes, so any field you have added survives.
- The upgrade plan reports how much of the range is covered by release
  notes, so a partly documented range reads as partial rather than
  appearing complete.

### Notes
- Write-once files are unchanged by this release and stay write-once:
  `server.js`, `package.json`, `.gitignore`, `docs/` and `scripts/` are
  created once, never overwritten, and never recreated if you delete them.
- An upgrade will not perform a breaking step for you. It copies files.
  Anything under Breaking here needs your hand.
