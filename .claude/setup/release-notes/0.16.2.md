### Fixes
- `/harness-upgrade` now shows you what breaks. It used to fetch the release
  notes from the GitHub releases API, which fails with a 403 in any sandboxed
  agent session (Claude Code on the web included), because the template repo
  is never attached to the session you are upgrading from. The skill treated
  that as a minor inconvenience and carried on, so the Breaking section, the
  one part of a plan describing work the file copy does not perform, went
  missing on every such run. The notes now travel inside the tree the upgrade
  already clones, so the narrative works offline, behind a proxy and with no
  credential. Where a target version is too old to carry them, the skill says
  so loudly, in the place the Breaking items would have been, above the
  confirmation prompt.
- A config file you have diverged from on purpose is no longer presented as
  pending work. If your `railway.json` or `.env.example` sets every key the
  template's copy sets, the plan now says "expect no change" instead of
  listing a merge that would do nothing. `/harness-upgrade` also states the
  rule it always followed but never wrote down: a config merge only ever adds
  keys you are missing, and never changes a value you have already set.
- A list the template extends is reported rather than hidden. Where the
  harness adds a hook or a permission inside an existing list in
  `.claude/settings.json`, the plan now names that list and asks you, instead
  of reporting that nothing changed.
- The version stamp in `.harness-version` is written last, and only after a
  re-plan confirms every approved file actually landed. It used to be written
  straight after the copies, so a failed copy left your repo claiming a
  version it did not hold, and that stamp is the input to the next upgrade's
  plan.

### Improvements
- The `CLAUDE.md` size suggestion reads the budget your project states rather
  than applying a number of its own, so it no longer disagrees with the
  standard it is quoting.
- An upgrade now makes no GitHub API call at all. Version discovery and both
  tree fetches were already plain git; the release notes were the last thing
  that was not.

### Notes
- An upgrade is a reviewed commit, not an automatic push. It rewrites the
  workflows, skills and hooks that decide how every future session in your
  repository behaves, and no person wrote any of it. Read `git diff`, check
  that your workflows and hooks still run, and commit it yourself.
  `/harness-upgrade` now says this at the end of every run, including in
  sessions whose own instructions say to push completed work.
- The narrative fix is client-side, so it takes effect from your next upgrade
  onward rather than this one: the skill doing the reading is the one already
  installed in your repository. Upgrading to this version is what installs
  the version that can read them.
