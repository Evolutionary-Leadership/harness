# Server layers

Three layers, one direction. Dependencies point downward and never back up.

| Layer | Path | May import | Must not |
|---|---|---|---|
| 3. Boundary | `src/app/**/actions.ts`, `src/app/api/**/route.ts` | Services, Zod schemas | Contain business rules or SQL |
| 2. Domain | `src/server/services/` | Repositories, pure modules | Import the Drizzle client or a schema table |
| 1. Data | `src/server/repositories/` | Drizzle, schema | Know about sessions, Zod, or HTTP |

## Executor types

`src/lib/db.ts` exports three types, and which one a function takes is a
statement about transaction ownership.

| Type | Taken by | Because |
|---|---|---|
| `DbExecutor` | Every repository function, and service READERS | The identical code runs against the pool and inside a transaction, with no branching |
| `DbClient` | Service MUTATORS | A mutator owns its transaction boundary and picks the isolation level |
| `DbTransaction` | `runSerializable` bodies | Handed in by the transaction helper |

## The action wrapper

Every Server Action is built by `defineAction` in `src/lib/action.ts`. There is no
second way to make one.

It does four things in order: parse with Zod, require a session, delegate to a
service, map errors to codes. A handler that contains an `if` is a handler with a
business rule in the wrong layer.

The return shape has no exceptions:

```ts
{ ok: true, data } | { ok: false, error: { code, message }, fieldErrors? }
```

| Error | Code | Note |
|---|---|---|
| No session | `unauthenticated` | A VALUE, not a redirect. An optimistic client needs something to reconcile, not a 307 |
| Zod rejected the input | `validation` | Carries `fieldErrors` |
| Missing row, or someone else's row | `not_found` | Deliberately identical, so probing cannot distinguish them |
| A fixable rule violation | `conflict` | |
| Anything unrecognised | `unexpected` | Logged in full server side, opaque to the client |

**Nothing throws across the action boundary.** That is what makes the optimistic UI
safe rather than reckless. Why, and what was rejected: ADR 0006.

## Soft warnings

A warning travels on the SUCCESS path as `warnings: Warning[]` beside the data. A
duplicate note title is kept and reported this way, never rejected: refusing would
strand an optimistic row the user can already see. The client shows a toast.

## Transactions

`runSerializable(db, body)` retries Postgres `40001` (and `40P01`) up to 5 attempts
with jittered backoff.

**Because it retries, every body must be idempotent:**

| Requirement | How it is met here |
|---|---|
| Inserts use `ON CONFLICT` | `insertNote` does `onConflictDoNothing` then returns or refetches |
| Deletes target exact keys | `deleteNote` matches `(id, userId)` and reports whether a row went |
| Ids generated by the CALLER | The action mints the id; the body never calls `randomUUID()` |
| No side effects outside the database | The duplicate-title count runs AFTER the transaction resolves |

Only mutators whose result depends on a read need it. `updateNote` and
`setNoteArchived` are single-row writes with no read-derived value, so they stay at
READ COMMITTED, and their comments say so.

| Mutator | Isolation | Why |
|---|---|---|
| `createNote` | SERIALIZABLE | The new position is derived from reading its siblings |
| `moveNote` | SERIALIZABLE | The new order is derived from reading the current order |
| `updateNote` | READ COMMITTED | Single row, last write wins, which is what the editing user expects |
| `setNoteArchived` | READ COMMITTED | Single-row flag flip |
| `deleteNote` | READ COMMITTED | Exact key delete |

## Ownership

Every repository query has `userId` in its WHERE clause. Rows are never fetched and
then filtered: another user's note is invisible at the query level.
`tests/integration/notes-repository.test.ts` asserts invisible, unupdatable, and
undeletable as separate cases.
